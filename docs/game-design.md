# game-design.md — ゲームデザイン

対象: MVP（CASE 1本）。用語と進行モデルはそのまま実装の語彙になる。

---

## 1. コアループ

```
事件/目的を読む
   ↓
schema を見て「どのテーブルに答えがありそうか」を考える
   ↓
SQL を書く
   ↓
実行して結果表を見る
   ↓
┌─ 目的を満たす結果だった → 証拠を獲得 → ストーリーが進む → 次の目的
└─ 満たさない → 結果を手掛かりに書き直す（何度でも / ペナルティなし）
```

最後に **最終回答** を提出して事件を解決する。

### ループの設計原則

- **失敗コストをゼロにする。** 実行回数制限・時間制限・ライフは置かない。
  試行錯誤そのものが遊びなので、それを罰しない。
- **空結果も情報にする。** 0件は「そこには無い」という捜査結果。
  「0件でした」ではなく「該当する記録は見つかりませんでした」と表示する。
- **1クエリ = 1つの気づき。** 1つの目的が複数の発見を要求しない。
  目的を細かく割ることで詰まりどころを特定できるようにする。

## 2. 進行モデル（データ構造の語彙）

```
CASE
 └─ Objective（調査目的）×N   ← DAG。prerequisites で依存を表現
      ├─ Check（達成条件）×1..N  ← クエリ結果に対する判定
      ├─ Hint（ヒント）×0..N     ← 段階的に開示
      └─ Reward
           ├─ Evidence（証拠）×0..N   ← 恒久的にStoryに残る
           └─ StoryBeat（ストーリー断片）×0..N
 └─ FinalAnswer（最終回答）
```

### Objective（調査目的）

プレイヤーに提示される「いま調べること」。1つのObjectiveは1つの疑問に対応する。

- `prerequisites: ObjectiveId[]` — これが全て `completed` になると `active` になる
- **並行可**: prerequisitesが同じ複数のObjectiveは同時にactiveになる（順不同で解ける）
- **判定対象は「activeな全Objective」**。プレイヤーが先回りして大きなJOINを1発で書いた場合、
  そのクエリで満たせるactiveなObjectiveはすべて同時に達成される。
  これは「上手いプレイが報われる」ための仕様であって、バグではない。
- 逆に、prerequisitesを満たしていないObjectiveは、たまたま結果が一致しても達成されない。
  ストーリー順序が壊れるのを防ぐため。

### Check（達成条件）

**SQL文字列は一切見ない。実行結果だけを見る。** 詳細な判定仕様は
[case-format.md](./case-format.md#5-判定仕様check) を参照。判定の種類は3つ:

| 種類 | 意味 | 使いどころ |
|---|---|---|
| `resultSet` | 結果表が期待する行集合と一致する | 「該当する取引を1件に絞り込め」 |
| `containsRows` | 結果表が期待行を**含む**（余分な行・列があってもよい） | 「犯行時刻にログインしていた人物を見つけろ」 |
| `columnValues` | 特定列の値集合が一致する | 「関与した3名を特定しろ」 |

MVPは `containsRows` を基本とする。`resultSet` の完全一致はプレイヤーに
「列の並びと余計な列を消す」という捜査と無関係な作業を強いるため、
**「この列だけを出せ」がストーリー上の要求である場合に限って**使う。

### Evidence（証拠）

獲得すると Story 画面に永続表示されるカード。ID・タイトル・本文・獲得時刻を持つ。
セーブデータに残り、リロードしても消えない。

### Hint（ヒント）

Objectiveごとに `level: 1..n` の配列。プレイヤーが明示的に押したときだけ開示される。
段階は原則3層:

1. **方向** — 「取引記録を金額で絞ってみましょう」（どのテーブルか）
2. **手法** — 「`WHERE amount >= 1000000` のように条件を付けます」（どのSQL構文か）
3. **ほぼ答え** — 具体的なクエリの形（正解SQLそのものは載せない。書き方は複数あるため）

開示済みヒントはセーブデータに記録する（クリア時の「ヒント使用数」表示と、
プレイテストでの詰まりどころ計測に使う）。**ヒント使用にペナルティは付けない。**

### FinalAnswer（最終回答）

自由入力ではなく**構造化フォーム**にする。

- 「犯人は誰か」→ 容疑者リストからの選択（selectタイプ）
- 「手口は」→ 選択肢からの選択
- 必要に応じて複数フィールド

自由テキストにしない理由: 表記ゆれ判定はゲームの本質ではなく、
「田中」「田中太郎」「TANAKA」の吸収に労力を割く価値がない。

不正解時は「その推理では説明できない点があります」と返し、**回数制限は設けない**。
どこが違うかは言わない（総当たりを防ぐため、選択肢は十分な数を用意する）。

## 3. 難易度カーブ

CASE内でSQL概念を段階的に登場させる。1つのObjectiveで新概念は1つまで。

| 段階 | SQL概念 | CASE 001での対応 |
|---|---|---|
| 1 | `SELECT` / `WHERE` / `ORDER BY` | 高額取引を探す |
| 2 | `JOIN` | employee_id から人物を特定する |
| 3 | 日時比較 / 範囲条件 | 送金時刻とログイン記録を突き合わせる |
| 4 | `GROUP BY` / `HAVING` / 集計 | 不自然な行動パターンを見つける |
| 5 | サブクエリ | 「〜でない人物」を絞り込む |
| 6 | CTE / Window Function | （CASE 002以降。CASE 001では必須にしない） |

**重要**: 高度な構文を*必須*にしない。CASE 001の全Objectiveは、
段階5までの知識で解ける状態を保つ。CTEやWindow Functionは「使えば楽になる」
オプショナルな近道として存在させる。

## 4. 画面と情報設計

MVPは4領域。デスクトップは2カラム、モバイルはタブ切替。

```
┌────────────────┬─────────────────────────┐
│  Story         │  Database               │
│  - 事件概要    │  - テーブル一覧          │
│  - 現在の目的  │  - カラム/型/説明        │
│  - 獲得済み証拠│                         │
│  - ヒント      ├─────────────────────────┤
│  - 最終回答へ  │  SQL Editor             │
│                │  [実行] Cmd/Ctrl+Enter  │
│                ├─────────────────────────┤
│                │  Result                 │
│                │  - 結果表 / エラー       │
│                │  - 行数・実行時間        │
└────────────────┴─────────────────────────┘
```

### Story 画面

- **事件概要**: 常に読み返せる（折りたたみ）
- **現在の目的**: activeなObjectiveを全て表示。複数あれば並べる
- **獲得済み証拠**: 時系列。新規獲得時はアニメーションで注意を引く
- **ヒント**: 目的ごとに「ヒントを見る」ボタン。押すたびに1段階開示

### Database 画面

**MVPで最も手を抜いてはいけない画面。** ここが貧弱だとプレイヤーは
「何を調べられるのか」が分からず、SQLを書く前に詰む。

- テーブル一覧と、各テーブルの1行説明
- カラム名・型・説明・NULL可否
- **サンプル行を3行程度表示**（型と値の雰囲気を掴ませる。`created_at` が
  `'2026-03-14 02:14:00'` なのか epoch なのかが分からないと詰む）
- テーブル間のリレーション（`transactions.employee_id → employees.id`）を明示
- テーブル名・カラム名はクリックでエディタに挿入できると望ましい（nice to have）

### SQL Editor

- MVPはシンタックスハイライト付きテキストエリアで十分。補完は不要
- 実行: ボタン + `Cmd/Ctrl + Enter`
- **実行履歴**: 過去に実行したクエリを遡れる（↑キー or 履歴リスト）。
  試行錯誤ゲームなので、これは quality-of-life ではなく必須に近い
- 複文（`;` 区切り）は最初の1文のみ実行するか、エラーにする（実装時に決定）

### Result 画面

- 表形式。列名ヘッダ固定、横スクロール可
- **NULLは空文字ではなく `NULL` とグレー表示**（区別できないと捜査が破綻する）
- 行数と実行時間を表示
- 表示上限（例 500行）を設け、超過時は「先頭500行を表示（全 N 件）」と明示
- **エラーは日本語に翻訳して出す**（下記5）

## 5. エラーとフィードバックのUX

SQLiteの生エラーは初中級者に厳しい。生メッセージも残しつつ、既知パターンは翻訳する。

| SQLiteのエラー | 表示 |
|---|---|
| `no such table: employee` | テーブル `employee` は存在しません。Database画面のテーブル一覧を確認してください。（もしかして: `employees`） |
| `no such column: nmae` | カラム `nmae` は存在しません。（もしかして: `name`） |
| `near "FROM": syntax error` | `FROM` の手前に文法エラーがあります。 |
| `ambiguous column name: id` | `id` がどのテーブルの列か特定できません。`employees.id` のように書いてください。 |

「もしかして」は既存のテーブル名/カラム名とのレーベンシュタイン距離で出す。

**書き込み系SQLの扱い**: `INSERT` / `UPDATE` / `DELETE` / `DROP` / `ATTACH` などは
実行前に拒否し、こう返す:

> このゲームでは記録の**閲覧**のみ可能です。捜査資料を書き換えることはできません。

エラーではなく世界観に沿ったメッセージにする。詳細は
[architecture.md](./architecture.md#6-クエリガード) を参照。

## 6. セーブとリセット

- 保存先: `localStorage`（キー: `sql-mystery:progress:v1:<caseId>`）
- 保存内容: 完了Objective、獲得Evidence、開示済みヒント、クエリ履歴、最終回答の試行回数
- **保存しない**: 現在のエディタ内容以外の一時状態
- バージョン不整合（CASEデータ更新後など）はセーブを破棄して最初からにする。
  黙って壊れるより明示的に作り直す
- 「最初からやり直す」ボタンを設ける（確認ダイアログ付き）

## 7. クリア体験

最終回答が正解したら:

1. 真相の解説（`epilogue`）を表示 — **ここが一番の報酬**。
   どのデータがどう繋がって真相に至ったかを、獲得した証拠を引用しながら説明する
2. プレイ記録: 所要時間 / 実行クエリ数 / ヒント使用数
3. 「もう一度遊ぶ」「（将来）次の事件へ」

**アンチパターン**: クリア画面で「あなたはSQLのJOINを習得しました！」のような
学習達成バッジを出さない。SQLは道具であって目的ではない、というプロダクトの
立て付けを自分で壊すことになる。

## 8. CASE 001 のストーリー骨格

詳細は [cases/case-001.md](./cases/case-001.md)。設計上のポイントだけ:

- 導入: 深夜02:14に1,000,000円の不正送金
- 素直に辿ると、送金を実行したアカウントの持ち主にたどり着く
- しかしその人物は**その時刻にオフィスにいない / ログインできない状況**にある
- 認証情報が使われた形跡を別テーブルから見つけると、真犯人が浮かぶ
- **どんでん返しは1回だけ。** 2段3段のひねりはMVPでは検証コストに見合わない

目標プレイ時間 30〜60分 = Objective 6〜8個程度、1つあたり4〜7分。
