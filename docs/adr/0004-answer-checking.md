# ADR-0004: 正解判定はSQL文字列ではなく結果で行う

- 状態: **Accepted**
- 日付: 2026-08-22

## コンテキスト

「正解」をどう定義するか。SQL文字列の比較（正規化 + 一致、またはAST比較）と、
実行結果の比較がありうる。

## 決定

**SQL文字列を一切見ない。実行結果のみで判定する。**

以下は同じ結果を返すので、どちらも正解として扱う。

```sql
SELECT name FROM employees WHERE id = 3;
SELECT e.name FROM employees e WHERE e.id = 3;
SELECT name FROM employees WHERE id IN (SELECT 3);
```

## 理由

- **プロダクトの根幹**（[vision.md](../vision.md)）。「同じ答えに複数の道で到達できる」ことが
  現実のデータ分析に近く、本プロダクトの価値そのもの
- SQL文字列の正規化は原理的に破綻する。エイリアス、空白、句の順序、
  等価な結合の書き換え、`IN` と `EXISTS` の相互変換……全てを吸収することはできない
- AST比較でも「意味的に等価だが構造が異なるクエリ」は正規化しきれない
- 結果比較は**エンジン非依存**。PostgreSQL移行時も期待値をそのまま使える
  （[ADR-0001](./0001-sql-engine.md)）

## 実装方針

判定は3種類（`resultSet` / `containsRows` / `columnValues`）。
値の正規化ルールは [case-format.md §5](../case-format.md#5-判定仕様check) で厳密に定義する。

MVPは `containsRows` を基本とする。完全一致（`resultSet`）は、
「余計な列を消す」「行順を揃える」といった**捜査と無関係な作業**を強いるため、
それ自体がストーリー上の要求である場合に限定する。

## 将来の拡張

「結果の一致」から「ゲームイベントの発生」へ拡張しうる。例:

- 特定の行が結果に**現れた**ことをもって証拠獲得（今の `containsRows` はこれの原型）
- 複数クエリにまたがる状態（「Aを見た後にBを見た」）
- 集計値が閾値を超えた

`Check` を判別可能ユニオン（`type` フィールド持ち）にしておくことで、
種類の追加が既存CASEを壊さない形でできる。
