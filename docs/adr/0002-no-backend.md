# ADR-0002: MVPではバックエンドを作らない

- 状態: **Accepted**
- 日付: 2026-08-22

## コンテキスト

SQL実行をサーバー側DBで行う構成も取りうる。その場合、正解情報を秘匿でき、
PostgreSQLをそのまま使える。一方で以下が必要になる。

- SQL実行API、DB接続管理、コネクションプール
- ユーザーSQLをDBに流すことによる攻撃面（権限分離、`statement_timeout`、行数上限、
  スキーマ分離、レート制限）
- DBサーバーの運用費と可用性

## 決定

**MVPはバックエンドを作らない。** SQL実行はブラウザ内SQLite WASM、
CASEデータは静的アセットとして配信する。

## 理由

- CASEデータは**固定・読み取り専用**。サーバーで動的に用意するものが何もない
- MVPの検証対象は「ゲームとして面白いか」であり、インフラは検証対象ではない
- 運用費がほぼゼロになり、検証に時間をかけられる
- ユーザーSQLをサーバーDBへ流さないため、MVPで対処すべきセキュリティ課題が激減する

## トレードオフ（受容する）

- **正解情報がDevToolsで見える。** 静的配信の必然。技術で防がず、
  「見たら面白くない」という設計で対処する（[vision.md §6](../vision.md#6-意図的に受け入れる制約)）
- ランキング・不正防止・競技性は成立しない。Phase 7以降の課題とする
- SQLite方言に固定される。PostgreSQL移行は [ADR-0001](./0001-sql-engine.md) の
  `SqlEngine` 境界で担保する

## 再検討のトリガー

- 競技性・スコアリングが必要になった
- 正解の秘匿が要件になった
- CASE DBが静的配信に耐えないサイズになった
