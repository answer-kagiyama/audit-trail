# ui-layout.md — 調査画面のレイアウト設計

> 対象は**調査画面**（`/case-00X`）のみ。事件簿・オンボーディングは
> [game-design.md §4](./game-design.md#4-画面と情報設計) のまま変えない。

調査画面には Story / Database / SQL Editor / Result の4面がある。
これらをどこにどう置くかを、実測値と各面の性質から決める。

計測はすべて `vite preview` + Chromium、CASE 002（5テーブル・リレーション5本、
`erCanvas` 900×520、図の実サイズ 852×441）で行った。以降の px はすべて実測値。

参考になる定数（実測）:

|  | 値 |
|---|---|
| エディタの1行 | 25.5px |
| エディタのパネル内で入力欄以外が使う高さ | 85px（タブ列 + ツールバー） |
| 結果表の1行 | 31px（見出し行は 29px） |
| Result パネル内で表以外が使う高さ | 40px |
| Database パネル内で図以外が使う高さ | 96px（見出し 33 + タブ列 39 + 余白 24） |

---

## 1. なぜ設計し直すのか

縦の取り合いが**ゼロサム**になっていて、片方を広げると片方が潰れる。

`.shell { height: 100% }` なので画面はどこにもスクロールしない。
ヘッダと余白を除いた高さを Database / Editor / Result の3面が分け合う。
その総量は 13インチノート（1280×620）で **539px** しかない。

| 画面 | 3面に使える高さ |
|---|---|
| 1280×620 | 539px |
| 1440×720 | 639px |
| 1920×860 | 779px |
| 2560×1300 | 1219px |

直近の変更（PR #13）は、この綱引きの一方に振っただけだった。

| 画面 | 変更前 DB / **入力欄** / Result | PR #13 後 |
|---|---|---|
| 1280×620 | 195 / **112**(4.4行) / 122(1.7行) | 146 / 123(4.8行) / 161(3.0行) |
| 1440×720 | 257 / **112**(4.4行) / 160(2.9行) | 194 / 123(4.8行) / 213(4.6行) |
| 1920×860 | 343 / **112**(4.4行) / 214(4.7行) | 252 / 141(5.5行) / 277(6.7行) |
| 2560×1300 | 614 / **112**(4.4行) / 384(10.2行) | 398 / 273(10.7行) / 438(11.9行) |

（Database と Result はパネルの高さ、真ん中は**入力欄そのもの**の高さ。
括弧内は入る行数。§5.3 の表はすべてパネルの高さで揃えてある。）

エディタの入力欄が全画面で 112px 固定だった問題は直ったが、その分は Database から取っている。
**「Database が狭い」という指摘は正しい。**

ただし、綱引きの調整だけでは解決しない。次節がその理由になる。

## 2. 実測でわかったこと

### 2.1 ER図はパネルからはみ出していて、半分以上が見えていない

`ErDiagram.module.css` の `.wrap` が `height: 100%; min-height: 20rem`、
親（`.erPanel`）は `flex-direction: column` の `overflow: visible`。
`height: 100%` が解決できないぶん `min-height` が勝ち、
**枠は親の高さに関係なく常に 318px 固定**になっている。

| 画面 | Database パネル | ER図の枠 | 実際に見えている縦幅 |
|---|---|---|---|
| 1280×620 | 144px | 318px | **55px（17%）** |
| 1920×860 | 250px | 318px | **161px（51%）** |
| 2560×1300 | 398px | 318px | 308px（96%） |

はみ出した分は `Panel` の `.body { overflow: auto }` でスクロールはできる。
できるが、13インチでは**縦 55px のスリットから 318px の図を覗く**ことになる。
これが「ER図が見づらい」の正体で、行の配分だけの問題ではない。

同じ理由で、**凡例（PK / FK / 三又の先）と「リレーションを文章で読む」は、
デスクトップのどの画面幅でも一度も表示されていない。**
後者は図の代替表現なので、事実上アクセシビリティの穴になっている。

### 2.2 枠が横長すぎて、面積の半分以上が捨てられている

図の縦横比は 1.93 : 1。対して枠は横に広い。
SVG は既定の `xMidYMid meet` なので**縦に合わせて縮み、左右に余白が出る**。

| 画面 | 枠の比率 | 描画倍率 | 枠の面積のうち図が使う割合 |
|---|---|---|---|
| 1280×620 | 2.72 : 1 | 0.72 | 71% |
| 1440×720 | 3.22 : 1 | 0.72 | 60% |
| 1920×860 | 4.73 : 1 | 0.72 | 41% |
| 2560×1300 | 6.74 : 1 | 0.72 | **29%** |

倍率が全画面で 0.72 なのは 2.1 の枠固定のため。
**WQHD の広い画面でも図は一切拡大されない。**
箱の中の文字は 11px 相当に縮んだままで、枠の 71% が空白になっている。

### 2.3 常時表示で ER図を等倍にするのは、13インチでは物理的に不可能

図を等倍（852×441）で出すには、見出し・タブ列・余白・凡例を含めて
**566px（約 35rem）**要る。13インチで3面に使える高さは 539px。
**Database ひとつで足が出る。**

つまり「Database の行をもっと大きくする」は、そのサイズのモニタでは成立しない。
どれだけ配分を工夫しても、常時表示のままでは ER図は読める大きさにならない。

### 2.4 Story は内部スクロールしていて、それは問題ない

| 画面 | Story の高さ | 中身の高さ |
|---|---|---|
| 1280×620 | 539px | 928px |
| 1920×860 | 779px | 928px |
| 2560×1300 | 1219px | 1179px |

13〜FHD ではスクロールする。ただし事件概要は2つ目の目的からは自動的に畳まれ、
その状態の中身は約 600px なので実害は小さい。
幅 22rem は日本語で1行 45文字前後にあたり、読みやすさの上限に近い。
**Story は変えない。**

## 3. 4つの面の性質

置き場所は「形」と「使う頻度」で決まる。

| 面 | 欲しい形 | 使うタイミング | 性質 |
|---|---|---|---|
| Story | 縦長・狭くてよい（22rem） | 目的の切り替わりごと | 常に目に入っていてほしい**現在地** |
| Database | 横長（1.93:1）・**大きさが要る** | クエリを書き始める前 | **参照**。見る時間は短く、深い |
| SQL Editor | 横幅と 7〜12 行 | 常時 | **ループ**の片側 |
| Result | 横幅と行数 | 常時 | **ループ**のもう片側 |

いちばん大事な区別はこれ。

- **Editor と Result は1回の試行で必ず両方使う。同時に見えていないと成立しない。**
- **Database はそうではない。**「どのテーブルがあって、どう繋がるか」を掴むのは
  クエリを書き始める前の数十秒で、打鍵中に見続けるものではない。
  打鍵中に要るのは列名——つまり ER図ではなく**テーブル詳細**のほう。

いまのレイアウトは3つを同じ縦の列に等しく並べているせいで、
「常に要るもの」と「たまに大きく要るもの」が同じ予算を奪い合っている。

## 4. 検討した案

### 案A: 全体を縦に流してスクロールさせる

`.workbench` に `overflow-y: auto` を入れ、各面に下限の高さを与える。

- ○ どの面も潰れない。実装が小さい
- × 下限の置き方を誤ると、13インチで **Editor と Result が同時に見えなくなる**。
  実行ボタンを押したら結果が画面外、という事故が起きる
- △ 「Editor + Result の下限の和 ≤ 13インチで使える高さ（539px）」を守れば防げる

### 案B: 3カラムにして Database を横に出す

`Story | Editor+Result | Database`。

- FHD で Database に 480px を割り当てると、枠は 480×779 の**縦長**。
  図は 1.93:1 なので横に合わせて縮み、**倍率 0.56 — いまより悪い**
- 図を縦長に組み替えれば別だが、`erCanvas` と座標は CASE データ側にあり、
  2ケース分の再設計と幾何テスト（交差・近接・箱の貫通）のやり直しが要る
- **却下。**横長の図を縦長の枠に入れる案は、原理的に得をしない

### 案C: Database を常設からはずし、開いたときだけ全面に出す

ワークベンチは Editor + Result の2段にし、Database はオーバーレイで開く。

- ○ 両方の不満が同時に消える。スクロールもしない
- × **初見のプレイヤーに ER図が見えない。**
  「まずデータベースの構造を見る」がこのゲームの入口なので、
  それを1クリック奥に隠すのは損が大きい

### 案D（採用）: 小窓は残し、「拡大」を用意し、足りない画面だけ流す

案Aと案Cの組み合わせ。役割をこう分ける。

- **常設の Database は「全体の当たり」を付けるサムネイル。**箱の数と位置、
  線の走り方が分かればよい。テーブル詳細タブはここで完結する
- **図を読むのは「拡大」で行う。**等倍以上で出す
- **収まらない画面でだけワークベンチを縦に流す。**収まる画面では流さない

## 5. 採用する設計

### 5.1 全体の骨格（変えない）

```
┌─────────────────────────────────────────────────────────┐
│ WHERE  / 事件名                     遊び方 事件簿 テーマ  │  ヘッダ（固定）
├──────────────┬──────────────────────────────────────────┤
│ Story        │ ┌ Database ───────────── [拡大] [畳む] ┐ │
│  進捗バー    │ │  ER図 | テーブル詳細                  │ │
│  事件概要    │ │  凡例 / リレーションを文章で読む       │ │
│  調査目的    │ └──────────────────────────────────────┘ │
│  ヒント      │ ┌ SQL Editor ─────────────────────────┐ │
│  証拠        │ │  タブ / 入力 / [実行]                 │ │
│  最終回答へ  │ └──────────────────────────────────────┘ │
│              │ ┌ Result ──────────────────────────────┐ │
│ (内部スクロール)│ │                                       │ │
└──────────────┴─┴──────────────────────────────────────┴─┘
   22rem 固定      ここだけ、収まらなければ縦にスクロールする
```

ヘッダと Story は動かない。**スクロールするのは右カラムだけ。**
Story を一緒に流さないのは、「いま何を調べているか」を見失わせないため。

### 5.2 変更1: ER図の枠のサイズ計算を直す（バグ修正）

```css
/* ErDiagram.module.css */
.wrap {
  flex: 1; /* 追加: 親の残りを使う */
  min-height: 6rem; /* 20rem から下げる。はみ出しの原因を外す */
  /* height: 100% を削除 */
}
```

枠が Database パネルの高さに追従し、はみ出しが止まる。
**凡例と「リレーションを文章で読む」がデスクトップでも初めて見えるようになる。**

あわせて、いま縦に2段積んでいる凡例（29px）と代替一覧（28px）を**1行にまとめる**。
パネルは横に 892〜2172px あり、横方向は余っている。57px → 29px。

### 5.3 変更2: 右カラムの下限とスクロール

```css
.workbench {
  display: grid;
  grid-template-rows:
    minmax(14rem, 0.8fr) /* Database: サムネイルとして成立する最小 */
    minmax(16rem, 1fr) /* Editor:   入力欄が 6.7 行 */
    minmax(14rem, 1.2fr); /* Result:   見出し + 5 行 */
  gap: var(--space-3);
  overflow-y: auto; /* 下限の合計に足りなければ流す */
  min-height: 0;
}
```

下限の合計は 44rem + 隙間 24px = **728px**。画面ごとの結果はこうなる。

| 画面 | 使える高さ | 挙動 | Database | Editor | Result |
|---|---|---|---|---|---|
| 1280×620 | 539 | **189px 流れる** | 224（図 0.22倍） | 256（6.7行） | 224（5.0行） |
| 1440×720 | 639 | **89px 流れる** | 224（0.22倍） | 256（6.7行） | 224（5.0行） |
| 1920×860 | 779 | 収まる | 238（0.26倍） | 273（7.4行） | 244（5.6行） |
| 2560×1300 | 1219 | 収まる | 355（0.52倍） | 420（13.1行） | 420（11.3行） |

PR #13 との差分。

| 画面 | Database | Editor | Result |
|---|---|---|---|
| 1280×620 | 146 → **224** | 4.8 → **6.7行** | 3.0 → **5.0行** |
| 1440×720 | 194 → **224** | 4.8 → **6.7行** | 4.6 → **5.0行** |
| 1920×860 | 252 → 238 | 5.5 → **7.4行** | 6.7 → 5.6行 |
| 2560×1300 | 398 → 355 | 10.7 → **13.1行** | 11.9 → 11.3行 |

13〜14インチは全面が改善する。FHD 以上は Result が 1行ぶん減る——
そこは 779px を3つで割る以上どうにもならないので、**エディタに寄せる判断**を取る。
結果表は元々スクロールする面であり、入力欄と違って「見えている行数」が
思考を止めることはない。

#### 「無理に1ページに収めない」の適用範囲

流すのは**収まらない画面だけ**にする。FHD 以上でも一律に流すと、
「スクロールしないと Result が無い」状態を、必要のない画面にまで広げてしまう。

そして下限は「**Editor と Result の和 ≤ 539px**」を必ず満たすように置く
（16rem + 隙間 + 14rem = 492px ≤ 539px）。
これにより、13インチで Database を通り過ぎたあとは
**Editor と Result が必ず同時に見える。**中核のループは壊れない。

#### 流れている状態で実行したとき

Database を見上げたまま実行する経路は残る。そこで、

> **実行後、Result パネルが画面内に入っていなければスクロールして見せる。**

を併せて入れる。`scrollIntoView({ block: 'nearest' })` で足り、
すでに見えているときは何も起きない。

### 5.4 変更3: Database に「拡大」を足す

`Panel` の見出しに「畳む」と並べて **「拡大」** を置く。
押すとダイアログ（Base UI `Dialog`、`92vw × 88vh`）で Database を開く。
中身は同じ ER図 / テーブル詳細のタブで、選択中のタブは小窓と共有する。

ER図の描画倍率がこう変わる。

| 画面 | いま | 拡大後 |
|---|---|---|
| 1280×620 | 0.72（うち **17%** しか見えない） | **0.88**（全体が見える） |
| 1440×720 | 0.72（うち 32%） | **1.07** |
| 1920×860 | 0.72（うち 51%） | **1.35** |
| 2560×1300 | 0.72（うち 96%） | **2.23** |

- 閉じるのは Esc / 背景クリック / 「閉じる」
- 開いている間はエディタが見えない。**それでよい**——
  §3 のとおり、ER図を読むのは打鍵中ではない
- 打鍵中に列名を見たい場面は、小窓の**テーブル詳細**タブが受け持つ。
  こちらは縦スクロールするテキストなので、小窓でも用を成す
- モバイルでは Database タブがすでに全面だが、拡大は同じダイアログでそのまま効く
- パン / ズームは小窓でも拡大でも従来どおり使える。
  小窓で一部を大きく見たいときはそちらで足りる

「畳む」（`useLayoutPreference`）はそのまま残す。畳んだときの配分はこう置く。

```css
.workbench[data-database-collapsed="true"] {
  grid-template-rows: auto minmax(15rem, 1fr) minmax(14rem, 1.2fr);
}
```

下限の合計は 41（見出しだけ）+ 240 + 224 + 隙間 24 = **529px ≤ 539px**。
**13インチでもスクロールが消える。**「拡大」があるので、
Database を畳んだままでも図は読める。

### 5.5 Story とモバイル

- **Story は変更しない。**22rem 固定、内部スクロール、
  事件概要は2つ目の目的から自動で畳まれる
- **モバイル（<900px）のタブ構成も変更しない。**Story / Database / SQL の3タブ。
  Editor と Result は同じタブに置く（ループを分断しないため）

## 8. 決めなかったこと

- **面の境界をドラッグで動かせるようにする**（スプリッタ）。
  自由度は上がるが、既定値の設計から逃げているだけで、初見のプレイヤーは触らない。
  まず既定を正す
- **`erCanvas` を縦長に組み替える**。案Bの前提で、CASE データ側の再設計が要る。
  横長のままで拡大するほうが安い
- **Story の幅を画面に応じて広げる**。1行45文字は既に読みやすさの上限で、
  広げても得がない
- **Story を上部の横帯にする**。目的の文章は縦に流れるほうが読みやすく、
  横帯にすると証拠とヒントの置き場所が無くなる
- **Story を右カラムと一緒に流す**。現在地を見失わせないため、常に固定する
