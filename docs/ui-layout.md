# ui-layout.md — 調査画面のレイアウト設計

> 対象は**調査画面**（`/case-00X`）のみ。事件簿・オンボーディングは
> [game-design.md §4](./game-design.md#4-画面と情報設計) のまま変えない。

調査画面には Story / Database / SQL Editor / Result の4面がある。
これらをどこにどう置くかを、実測値と各面の性質から決める。

計測はすべて `vite preview` + Chromium、CASE 002（5テーブル・リレーション5本、
`erCanvas` 900×520、図の実サイズ 852×441）で行った。以降の px はすべて実測値。

参考になる定数（実測）:

|  | 値 |
|---|---|
| エディタの1行 | 25.5px |
| エディタのパネル内で入力欄以外が使う高さ | 85px（タブ列 + ツールバー） |
| 結果表の1行 | 31px（見出し行は 29px） |
| Result パネル内で表以外が使う高さ | 40px |
| Database パネル内で図以外が使う高さ | 96px（見出し 33 + タブ列 39 + 余白 24） |

---

## 1. なぜ設計し直すのか

縦の取り合いが**ゼロサム**になっていて、片方を広げると片方が潰れる。

`.shell { height: 100% }` なので画面はどこにもスクロールしない。
ヘッダと余白を除いた高さを Database / Editor / Result の3面が分け合う。
その総量は 13インチノート（1280×620）で **539px** しかない。

| 画面 | 3面に使える高さ |
|---|---|
| 1280×620 | 539px |
| 1440×720 | 639px |
| 1920×860 | 779px |
| 2560×1300 | 1219px |

直近の変更（PR #13）は、この綱引きの一方に振っただけだった。

| 画面 | 変更前 DB / **入力欄** / Result | PR #13 後 |
|---|---|---|
| 1280×620 | 195 / **112**(4.4行) / 122(1.7行) | 146 / 123(4.8行) / 161(3.0行) |
| 1440×720 | 257 / **112**(4.4行) / 160(2.9行) | 194 / 123(4.8行) / 213(4.6行) |
| 1920×860 | 343 / **112**(4.4行) / 214(4.7行) | 252 / 141(5.5行) / 277(6.7行) |
| 2560×1300 | 614 / **112**(4.4行) / 384(10.2行) | 398 / 273(10.7行) / 438(11.9行) |

（Database と Result はパネルの高さ、真ん中は**入力欄そのもの**の高さ。
括弧内は入る行数。§5.3 の表はすべてパネルの高さで揃えてある。）

エディタの入力欄が全画面で 112px 固定だった問題は直ったが、その分は Database から取っている。
**「Database が狭い」という指摘は正しい。**

ただし、綱引きの調整だけでは解決しない。次節がその理由になる。

## 2. 実測でわかったこと

### 2.1 ER図はパネルからはみ出していて、半分以上が見えていない

`ErDiagram.module.css` の `.wrap` が `height: 100%; min-height: 20rem`、
親（`.erPanel`）は `flex-direction: column` の `overflow: visible`。
`height: 100%` が解決できないぶん `min-height` が勝ち、
**枠は親の高さに関係なく常に 318px 固定**になっている。

| 画面 | Database パネル | ER図の枠 | 実際に見えている縦幅 |
|---|---|---|---|
| 1280×620 | 144px | 318px | **55px（17%）** |
| 1920×860 | 250px | 318px | **161px（51%）** |
| 2560×1300 | 398px | 318px | 308px（96%） |

はみ出した分は `Panel` の `.body { overflow: auto }` でスクロールはできる。
できるが、13インチでは**縦 55px のスリットから 318px の図を覗く**ことになる。
これが「ER図が見づらい」の正体で、行の配分だけの問題ではない。

同じ理由で、**凡例（PK / FK / 三又の先）と「リレーションを文章で読む」は、
デスクトップのどの画面幅でも一度も表示されていない。**
後者は図の代替表現なので、事実上アクセシビリティの穴になっている。

### 2.2 枠が横長すぎて、面積の半分以上が捨てられている

図の縦横比は 1.93 : 1。対して枠は横に広い。
SVG は既定の `xMidYMid meet` なので**縦に合わせて縮み、左右に余白が出る**。

| 画面 | 枠の比率 | 描画倍率 | 枠の面積のうち図が使う割合 |
|---|---|---|---|
| 1280×620 | 2.72 : 1 | 0.72 | 71% |
| 1440×720 | 3.22 : 1 | 0.72 | 60% |
| 1920×860 | 4.73 : 1 | 0.72 | 41% |
| 2560×1300 | 6.74 : 1 | 0.72 | **29%** |

倍率が全画面で 0.72 なのは 2.1 の枠固定のため。
**WQHD の広い画面でも図は一切拡大されない。**
箱の中の文字は 11px 相当に縮んだままで、枠の 71% が空白になっている。

### 2.3 常時表示で ER図を等倍にするのは、13インチでは物理的に不可能

図を等倍（852×441）で出すには、見出し・タブ列・余白・凡例を含めて
**566px（約 35rem）**要る。13インチで3面に使える高さは 539px。
**Database ひとつで足が出る。**

つまり「Database の行をもっと大きくする」は、そのサイズのモニタでは成立しない。
どれだけ配分を工夫しても、常時表示のままでは ER図は読める大きさにならない。

### 2.4 Story は内部スクロールしていて、それは問題ない

| 画面 | Story の高さ | 中身の高さ |
|---|---|---|
| 1280×620 | 539px | 928px |
| 1920×860 | 779px | 928px |
| 2560×1300 | 1219px | 1179px |

13〜FHD ではスクロールする。ただし事件概要は2つ目の目的からは自動的に畳まれ、
その状態の中身は約 600px なので実害は小さい。
幅 22rem は日本語で1行 45文字前後にあたり、読みやすさの上限に近い。
**Story は変えない。**

## 3. 4つの面の性質

置き場所は「形」と「使う頻度」で決まる。

| 面 | 欲しい形 | 使うタイミング | 性質 |
|---|---|---|---|
| Story | 縦長・狭くてよい（22rem） | 目的の切り替わりごと | 常に目に入っていてほしい**現在地** |
| Database | 横長（1.93:1）・**大きさが要る** | クエリを書き始める前 | **参照**。見る時間は短く、深い |
| SQL Editor | 横幅と 7〜12 行 | 常時 | **ループ**の片側 |
| Result | 横幅と行数 | 常時 | **ループ**のもう片側 |

いちばん大事な区別はこれ。

- **Editor と Result は1回の試行で必ず両方使う。同時に見えていないと成立しない。**
- **Database はそうではない。**「どのテーブルがあって、どう繋がるか」を掴むのは
  クエリを書き始める前の数十秒で、打鍵中に見続けるものではない。
  打鍵中に要るのは列名——つまり ER図ではなく**テーブル詳細**のほう。

Database / Editor / Result を同じ縦の列に等しく並べていたのが問題だった。
「常に要るもの」と「たまに大きく要るもの」が同じ予算を奪い合い、
どちらを立てても片方が潰れる。**Database を縦の列から外す**のが答えになる。

## 4. 検討した案

### 案A: 縦積みのまま、収まらない画面だけ流す

`.workbench` に `overflow-y: auto` を入れ、各面に下限の高さを与える。

- ○ 実装が小さい。どの面も下限を割らない
- × **ER図は救えない。**§2.3 のとおり、13インチで常時表示のまま
  読める大きさにするのは物理的に不可能
- 一度これを実装した（PR #15）。エディタと結果は確かに広がったが、
  ER図は 0.21倍のままで、**拡大しないと何も見えない**という指摘を受けた

### 案B: Database を独立した3本目のカラムにする ← **採用**

`Story | Editor+Result | Database`。カラム幅は掴み手で変えられ、左右は畳める。

**縦の取り合いを横に移す。**これが要点。

ER図は 852×441 の横長で、縦積みでは常に高さが先に尽きる。
独立したカラムにすると高さはカラム全体（FHD で 779px、必要な 441px の 1.7倍）
になり、**縛りが横幅だけ**になる。横幅は余っている次元なので、そちらで払える。

倍率はほぼ「カラム幅 ÷ 880」になる（図 852px ＋ 枠の余白 28px）。

| Database カラム幅 | ER図の倍率 |
|---|---|
| 縦積み（案A） | **0.21** |
| 400px | 0.44 |
| 600px | 0.67 |
| 880px | **1.00**（等倍。これ以上広げても図は大きくならない） |

さらに、幅を**プレイヤーが決められる**ことで、
ここまでずっと解こうとしてきた「誰にとって最適な配分か」という問題自体が消える。
何にどれだけ要るかは、その人がいま何を調べているかで変わる。

#### この案を一度却下したのは誤りだった

初版のこの節では「FHD で 480px を割り当てると倍率 0.56 — いまより悪い」と書いて却下した。
**この比較が間違っていた。**比較対象にした 0.72 は §2.1 のバグが出していた値で、
そのうち画面に出ていたのは 17〜51% でしかない。
バグを直したあとの実際の値は **0.21** なので、0.56 は 2.6倍の改善にあたる。

加えて「480px 固定では足りない」という前提も、幅が可変なら成り立たない。

### 案C: Database を常設からはずし、開いたときだけ全面に出す

ワークベンチは Editor + Result の2段にし、Database はオーバーレイでのみ開く。

- × **初見のプレイヤーに ER図が見えない。**
  「まずデータベースの構造を見る」がこのゲームの入口なので、
  それを1クリック奥に隠すのは損が大きい
- 「拡大」だけを残す形は実質これで、実際に「拡大しないと見えない」と言われた

## 5. 採用する設計

### 5.1 骨格

```
┌────────────────────────────────────────────────────────────────┐
│ WHERE  / 事件名                          遊び方 事件簿 テーマ   │ ヘッダ（固定）
├──────────────┬┬──────────────────────────┬┬──────────────────┤
│ Story  [畳む]││ ┌ SQL Editor ──────────┐ ││ Database [拡大][畳む]│
│  進捗バー    ││ │ タブ / 入力 / [実行]  │ ││  ER図 | テーブル詳細 │
│  事件概要    ││ └──────────────────────┘ ││                   │
│  調査目的    ││ ┌ Result ──────────────┐ ││   （カラム高さ全部） │
│  ヒント      ││ │                       │ ││                   │
│  証拠        ││ │                       │ ││                   │
│  最終回答へ  ││ └──────────────────────┘ ││  凡例 / 文章で読む  │
└──────────────┴┴──────────────────────────┴┴──────────────────┘
   幅可変・畳める↑              残り全部            ↑幅可変・畳める
              掴み手                            掴み手
```

- **縦のスクロールは無くなる。**真ん中は Editor と Result の2つだけなので、
  13インチ（539px）でも 256 + 8 + 224 = 488px に収まる
- 畳んだカラムは 28px のレールになり、押すと開く

### 5.2 幅の規則（`AppShell/columns.ts`）

| | 下限 | 既定 | 上限 |
|---|---|---|---|
| Story | 256px（1行 33文字） | 352px | 512px（1行 64文字） |
| 真ん中 | 448px | 残り全部 | — |
| Database | 288px | 残りの 45% | 880px（等倍） |

- **Database の上限が 880px** なのは、そこで図が等倍になり、
  それ以上広げても図は大きくならず真ん中を削るだけだから
- **既定を「残りの 45%」**にしたのは、初見でも ER図が読める大きさに寄せつつ、
  真ん中を窮屈にしないため
- **収まらないときは Database から先に削る。**Story は「いま何を調べているか」を
  出す面で、消えると現在地を見失う
- 幅は「利用者が望んだ値」をそのまま保存し、画面に収まるかは描画時に詰める。
  狭い画面で詰めた値を保存すると、広い画面に戻したときに戻らなくなる

既定のままの実測値。

| 画面 | Story | 真ん中 | Database | ER図 | 入力欄 | 結果表 |
|---|---|---|---|---|---|---|
| 1280×620 | 352 | 491 | 401 | **0.44倍** | 6.7行 | 6.6行 |
| 1440×720 | 352 | 579 | 473 | **0.52倍** | 7.9行 | 8.9行 |
| 1920×860 | 352 | 843 | 689 | **0.78倍** | 10.4行 | 11.3行 |
| 2560×1300 | 352 | 1292 | 880 | **1.00倍** | 18.2行 | 19.1行 |

縦積み（案A / PR #15）との差。

| 画面 | ER図 | 入力欄 | 結果表 | 縦スクロール |
|---|---|---|---|---|
| 1280×620 | 0.21 → **0.44** | 6.7 → 6.7行 | 5.0 → **6.6行** | 181px → **無し** |
| 1440×720 | 0.21 → **0.52** | 6.7 → **7.9行** | 5.0 → **8.9行** | 81px → **無し** |
| 1920×860 | 0.21 → **0.78** | 6.7 → **10.4行** | 6.9 → **11.3行** | 無し |
| 2560×1300 | 0.21 → **1.00** | 12.4 → **18.2行** | 13.3 → **19.1行** | 無し |

**どの画面でも、どの面も良くなる。**縦の取り合いが無くなったため。

### 5.3 掴み手

`role="separator"` + `aria-orientation="vertical"` + `aria-valuenow`。

- ドラッグ、**矢印キー**（Shift で4倍）で動かせる。
  スプリッタをポインタ専用にすると、キーボードだけで遊んでいる人は
  カラム幅を一生変えられない
- **ダブルクリック（キーボードなら Home）で既定に戻る。**
  動かしすぎて戻せなくなるのが、スプリッタで一番よくある詰まり方なので
- 幅は 6px だが、当たり判定は `::before` で左右に広げてある

### 5.4 「拡大」は残す

13インチでは Database カラムの上限が実質 444px（真ん中を守るため）で、
ER図は 0.49倍が精一杯。拡大はそこを超えるための逃げ道として残す。

| 画面 | カラム既定 | 拡大 |
|---|---|---|
| 1280×620 | 0.44倍 | 0.81〜0.93倍 |
| 1920×860 | 0.78倍 | 1.41倍 |
| 2560×1300 | 1.00倍 | 2.29倍 |

拡大の倍率は CASE の `erCanvas` の縦横比で変わる。
CASE 001（縦に長い）が最も不利で 0.81倍、CASE 002 は 0.93倍。

### 5.5 Story とモバイル

- **Story の中身は変えない。**内部スクロール、事件概要は2つ目の目的から自動で畳まれる。
  幅が可変になり、畳めるようになっただけ
- **モバイル（<900px）は変更しない。**Story / Database / SQL の3タブ。
  掴み手もレールも出さない（狭い画面で幅を分け合う余地が無い）

## 8. 決めなかったこと

- **`erCanvas` を縦長に組み替える**。カラムを縦長にする案の前提だが、
  CASE データ側の再設計と幾何テストのやり直しが要る。
  横長のままカラム幅で調整するほうが安い
- **真ん中を上下にも分割可能にする**。Editor と Result の比率も掴み手で
  変えられるようにする案。縦はもう取り合いになっていないので、
  必要になってからでよい
- **Story を上部の横帯にする**。目的の文章は縦に流れるほうが読みやすく、
  横帯にすると証拠とヒントの置き場所が無くなる
- **カラムの並び替え**。Database を左に置きたい人もいるかもしれないが、
  要望が出てからでよい
