# vision.md — プロダクトビジョン

## 0. プロダクト名

**Audit Trail**（監査証跡）

システムが残す「誰が・いつ・何をしたか」の記録そのものを指す言葉。
本作でプレイヤーが読み解くのは、まさにこの監査証跡である。

同時に「証跡を辿る（trail を追う）」という捜査行為の二重の意味を持たせている。
リポジトリ名・パッケージ名・localStorage キーは `audit-trail` で統一する。

## 1. 一言でいうと

**ブラウザ上で実際にSQLを書き、架空の事件のデータベースを調査して謎を解く推理ゲーム。**

SQLは「学習対象」ではなく「捜査の道具」として扱う。プレイヤーが解きたいのは事件であって、
SQLの練習問題ではない。SQLはその手段として自然に登場する。

## 2. なぜ作るのか

SQL学習サービスは多いが、そのほとんどが「問題を出す → 正解SQLと突き合わせる」形式で、
プレイヤーの動機が「正解すること」に閉じている。本プロダクトは動機を
**「事件の真相を知りたい」** に置き換える。

- クエリを書く理由が、外から与えられた課題ではなく、自分の知りたいことになる
- 「どう書くか」ではなく「何を知りたいか」を先に考える習慣がつく
- 同じ答えに複数のSQLで到達できる（＝現実のデータ分析に近い）

## 3. ターゲットユーザー

| 層 | 状態 | 本プロダクトで得るもの |
|---|---|---|
| 主ターゲット | `SELECT` / `WHERE` は書けるが、JOIN以降で手が止まる | ER図からリレーションを読み取り、JOIN・集計・サブクエリを使う必然性を体験する |
| 副ターゲット | SQLを学んだが実務で使ったことがない | 「調べたいことをクエリに翻訳する」プロセスの反復 |
| 副ターゲット | 謎解き・推理ゲーム好き | SQLというギミックの新しい謎解き体験 |

**非ターゲット（MVP時点）**: SQL完全初心者。`SELECT` の書き方から教えることはしない
（将来的にチュートリアルCASEで対応しうるが、MVPの検証対象ではない）。

## 4. コアバリュー

1. **調査の手触り** — 検索して、絞り込んで、突き合わせて、気づく
2. **複数の道** — 正解SQLは1つではない。結果が合っていればよい
3. **段階的な情報開示** — 一度に全部は見せない。1つ分かると次の疑問が生まれる
4. **どんでん返し** — 素直に辿った先が犯人ではない。データを組み合わせて初めて真相に届く
5. **データ構造を読む** — 事件のDBは**ER図**として提示される。
   どのテーブルがどう繋がっているかを読み取ることが、JOINを書く前段の思考になる

## 5. MVPスコープ

### やること

- CASEを1本（CASE 001「消えた100万円」）、開始からクリアまで通しで遊べる
- ブラウザ内SQLite WASMでのSQL実行
- Story / Database / SQL Editor / Result の4領域を持つ画面
- 結果ベースの正解判定（SQL文字列比較はしない）
- 段階的な調査進行（証拠獲得によるストーリー前進）
- 段階的ヒント
- 最終回答フォームとクリア画面
- 進捗のローカル保存（localStorage）
- 主要ゲームロジックの自動テスト
- 静的ホスティングで動作すること

### やらないこと（MVP非範囲）

| 非範囲 | 理由 / 将来の扱い |
|---|---|
| バックエンドAPI | 静的配信で成立する。サーバーはコストと攻撃面を増やすだけ |
| ユーザー認証・アカウント | 進捗はlocalStorageで足りる。Phase 7以降 |
| 複数CASE・CASE選択画面 | まず1本が面白いことを確認する。データ構造は複数前提で設計する |
| ランキング・実績・SNS共有 | 面白さの検証が先 |
| 課金 | 同上 |
| マルチプレイ・協力プレイ | 同上 |
| PostgreSQL実行エンジン | MVPはSQLite方言で仕様化。**ただし差し替え可能な境界は今設計する** |
| サーバー側での正解秘匿 | MVPはクライアント配信を前提とする（下記6参照） |
| 国際化（i18n） | 日本語のみ。文言はコードに直書きせずCASEデータ側に置く |

## 6. 意図的に受け入れる制約

- **正解情報はDevToolsで見える。** 静的配信である以上これは避けられない。
  MVPでは「見ようと思えば見られる」ことを前提に、カンニングを技術で防ぐのではなく
  「見たら面白くない」という設計で対処する。競技性が必要になった時点で
  サーバー判定（Phase 7+）を検討する。
- **SQLite方言に依存する。** 日付処理（`strftime`）、型の緩さ、`ILIKE` 不在など
  PostgreSQLとの差異がある。CASEデータは「SQLiteで動くSQLを書くゲーム」として仕様化し、
  UI上でもそれを明示する。
- **大規模データは扱わない。** CASE DBは数百〜数千行規模。ブラウザ内で完結させるための制約。

## 7. 成功指標（MVPの検証したいこと）

MVPは「売れるか」ではなく「面白いか」を検証する。

| 問い | 測り方（MVPでは定性で可） |
|---|---|
| 最後まで遊べるか | 実プレイテストで完走率を見る |
| 詰まるとしてどこか | 各調査ステップの所要時間・ヒント使用率 |
| SQLが「作業」ではなく「捜査」に感じられるか | プレイ後インタビュー |
| 目標プレイ時間30〜60分に収まるか | 実測 |
| どんでん返しが機能するか | 終盤の反応 |

**MVPのDefinition of Doneは [roadmap.md](./roadmap.md#definition-of-done) を参照。**

## 8. 将来像（MVPの外）

- CASEを複数本揃え、難易度カーブ（SELECT/WHERE → JOIN → GROUP BY/HAVING → サブクエリ → CTE → Window Function）で並べる
- CASE作成をエージェント／エディタで支援し、コンテンツ生産を分離する
- PostgreSQL実行エンジンを追加し、方言を選べるようにする
- サーバー判定モードによる競技・スコアリング
