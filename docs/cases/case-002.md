# CASE 002「改ざんされた在庫」仕様（設計）

- 難易度: 2
- 目標プレイ時間: **30〜60分**（CASE 001 の実測 20〜40分から導出。Objective 数は同じ7本で、
  1本あたりの難度とテーブル探索のコストが上がるぶんを 1.5 倍で見ている）
- 扱うSQL: `CASE`式 / 集計の応用 / **Window Function（累積和）** / **LEFT JOIN + IS NULL** /
  列どうしの比較 / `CTE`
- 前提: CASE 001 をクリアしている（`JOIN` と時刻の範囲条件は既知として扱う）

### 方言依存の関数は使わせない

`julianday()` や `strftime()` のような **SQLite 独自の関数を、解くために必須にしない**。
知らないと手が止まるが、それは推理で詰まっているのではなく関数名を知らないだけで、
「SQLは捜査の道具」（[vision.md §1](../vision.md)）という前提が崩れる。
ヒントで教える手もあるが、ヒントは**考え方**に使いたい。

日時は ISO 形式（`YYYY-MM-DD HH:MM:SS`）の TEXT で持つので、
**大小比較も期間の絞り込みも、素の比較演算子だけで足りる。** 関数は要らない。

**動作確認済み**（sql.js 同梱の SQLite **3.49.1** で実際に実行）:

| 構文 | 用途 | 結果 |
|---|---|---|
| `SUM(CASE ...) OVER (PARTITION BY ... ORDER BY ...)` | obj-03 の在庫推移 | ✓ |
| `LEFT JOIN ... WHERE ... IS NULL` | obj-05 の無承認廃棄 | ✓ |
| `WHERE created_at > occurred_at`（列どうしの比較） | obj-06 の遡及記録 | ✓ |

## 1. あらすじ

精密機器の物流を請け負う倉庫。四半期ごとに棚卸しを行い、帳簿在庫と実地在庫を突き合わせている。

2026年6月16日、本社監査の都合で**2週間前倒しされた**棚卸しで、
産業用センサー **SX-400**（単価80,000円）の実地在庫が帳簿より **12個少なかった**。
960,000円相当が、記録の上では存在するのに、棚に無い。

過去3回の棚卸し（2025-09-30 / 2025-12-31 / 2026-03-31）では差異はゼロだった。
だから一見、問題は直近3か月に起きたように見える。

**実際には、持ち出しは2025年の秋から続いていた。**

倉庫係の **相沢 亮** は、SX-400 を少しずつ持ち出しては、その分を
「破損廃棄」として計上し、棚卸しの直前に帳簿を合わせていた。
帳簿が合っている限り、差異は表に出ない。

破損廃棄には検品担当者の承認が必要だが、**彼の廃棄記録の一部には承認が無い**。
しかもそれらは、**起きたことにした日時よりずっと後に登録されている**——
棚卸しが近づいてから、過去に遡って書き足したからだ。

そして遡って挿入したせいで、**帳簿上の在庫が一時的にマイナスになる区間ができている。**
棚に無いものは出せない。物理的にありえない数字が、記録の中に残っている。

2026年6月は棚卸しが前倒しされたため、辻褄合わせが間に合わなかった。
だから12個だけが表面化した。

**真犯人: 相沢 亮。手口: 商品を持ち出し、架空の破損廃棄を計上して帳簿を合わせた。**

### このCASEの主題

CASE 001 の主題は「記録上の実行者 ≠ 実際にやった人」だった。
CASE 002 の主題は **「帳簿が合っている＝正常、ではない」**。

見えている差異（12個）は氷山の一角で、
**差異が出ていない期間のほうが、むしろ手が加えられている。**
この二段構えが、このCASEの推理としての核になる。

## 3. テーブル設計

### テーブル数を5にする判断

[case-001.md §4](./case-001.md) で「**4テーブルを上限とする**」と決めている。
CASE 002 では、これを1つ増やして5にする。理由:

- `disposal_approvals` を独立テーブルにしないと、**`LEFT JOIN` + `IS NULL`
  （「対応する行が存在しない」の検出）を教える場所がなくなる**。
  `movements.approved_by` を NULL 許容列にしてしまうと
  `WHERE approved_by IS NULL` で済み、このCASEの決定打が1行で終わる
- 難易度2は探索コストの上昇を織り込んだ帯である

ただし**5を新しい上限とする**。6以上はER図が放射状に破綻し、
Database画面の探索だけで持ち時間を使い切る。

### ER図

```
   products ──────< movements >────── staff
      │                 │               │
      │                 │               │
   stocktakes    disposal_approvals ────┘
```

| from | to | ラベル |
|---|---|---|
| `movements.product_id` | `products.id` | 動いた商品 |
| `movements.recorded_by` | `staff.id` | 記録した担当者 |
| `stocktakes.product_id` | `products.id` | 数えた商品 |
| `disposal_approvals.movement_id` | `movements.id` | 承認された廃棄 |
| `disposal_approvals.approver_id` | `staff.id` | 承認した検品担当 |

`movements` がハブ。`disposal_approvals` から2本出るので、
`movements` の真下に置き、`staff` へは右上へ伸ばす配置になる。
**実装時に必ず描画して線の交差を目視すること**（[case-format.md §8](../case-format.md)）。

| 列 | 型 | 説明 |
|---|---|---|

| `code` | TEXT | 型番（`SX-400` など）。プレイヤーが商品を指す時の鍵 |
| `name` | TEXT | 商品名 |
| `category` | TEXT | `sensor` / `cable` / `case` |
| `unit_price` | INTEGER | 単価（円）。被害額の算出に使う |

### staff（倉庫スタッフ）

| 列 | 型 | 説明 |
|---|---|---|
| `id` | INTEGER PK | |
| `name` | TEXT | |
| `role` | TEXT | `warehouse`（倉庫係）/ `inspector`（検品）/ `manager` |
| `status` | TEXT | `active` / `retired` |

`role` が効くのは「廃棄を承認できるのは `inspector` だけ」という業務ルール。
ストーリー本文と `schema.json` の `description` の両方に書く。

### movements（入出庫記録）— 中心テーブル

| 列 | 型 | 説明 |
|---|---|---|
| `id` | INTEGER PK | |
| `product_id` | INTEGER FK | → `products.id` |
| `kind` | TEXT | `in`（入庫）/ `out`（出庫）/ `disposal`（破損廃棄） |
| `quantity` | INTEGER | **常に正の数。符号は `kind` で決まる** |
| `occurred_at` | TEXT | 実際にモノが動いた日時 |
| `recorded_by` | INTEGER FK | → `staff.id` |
| `created_at` | TEXT | **記録がシステムに登録された日時** |
| `note` | TEXT | 摘要 |

> **`quantity` を常に正にするのは意図的**。
> 在庫を出すには `CASE WHEN kind = 'in' THEN quantity ELSE -quantity END` が要る。
> これが obj-03 の入口になる。符号付きで持たせると、この学びが消える。

> **`occurred_at` と `created_at` を分けるのが、このCASEの仕掛け**。
> 入出庫はハンディ端末でその場で登録されるので、
> **正規の記録は `created_at` と `occurred_at` が完全に一致する。**
> 遡って書き足された記録だけが `created_at > occurred_at` になる。
>
> この「正規は一致」という設計のおかげで、判定が
> **`WHERE created_at > occurred_at` という素の比較ひとつ**で済む。
> 「何日ずれているか」を測る必要が無くなり、`julianday()` を使わずにすむ。
>
> **列の説明文では「登録日時」としか書かない。**
> ストーリー側で「端末がその場で記録する」運用だけ伝え、
> 「ズレていたら後から作られた記録だ」とまでは書かない。そこは気づく側の仕事。

```
                                             └→ obj-07 ─┴→ 最終回答
```

| # | タイトル | 新しく登場するSQL | 得られる証拠 |
|---|---|---|---|
| **obj-01** | 棚卸しの記録を確かめる | （復習: `JOIN` / `WHERE`） | ev-01: 6月16日の棚卸しで SX-400 が12個足りない |
| **obj-02** | SX-400 の入出庫をすべて洗い出す | （復習）+ `kind` の存在に気づく | ev-02: 記録には入庫・出庫・**破損廃棄**の3種類がある |
| **obj-03** | 在庫の推移を再現する | **`CASE`式 + `SUM() OVER`（累積和）** | ev-03: 過去3回の棚卸しは合っている。だが**在庫がマイナスになる区間がある** |
| **obj-04** | 破損廃棄の記録に偏りがないか調べる | 集計の応用（比率の比較） | ev-04: **SX-400 だけ廃棄が突出している** |
| **obj-05** | 承認されていない廃棄を洗い出す | **`LEFT JOIN` + `IS NULL`** | ev-05: 承認のない廃棄が複数ある。**しかも過去にも** |
| **obj-06** | 後から書き足された記録を洗い出す | **列どうしの比較**（`created_at > occurred_at`） | ev-06: 無承認廃棄は、起きた日より後に登録されている |
| **obj-07** | 無承認廃棄を記録した人物を特定する | （復習: `GROUP BY` / `HAVING`） | ev-07: 相沢 亮 |

### 各Objectiveの狙い

**obj-01 / obj-02 は助走。** 5テーブルの構造とデータの語彙（`kind` の3値、
`quantity` が常に正であること）を、難しい操作抜きで掴ませる。
ここを飛ばすと obj-03 で「符号をどうするか」と「累積和」を同時に考えることになる。

**obj-03 が主役。** ここだけは Window Function が**代替不能**になるように組んである。

```sql
SUM(CASE WHEN kind='in' THEN quantity ELSE -quantity END)
  OVER (PARTITION BY product_id ORDER BY occurred_at)
```

狙いは「各棚卸し時点の在庫を出すこと」ではない——それは `GROUP BY` + `HAVING` で足りてしまう。
**狙いは、在庫が一度でもマイナスになった時点を見つけること。**

犯人は廃棄を過去に遡って挿入したが、その時点の実在庫を気にしていなかった。
結果、**帳簿在庫が一時的にマイナスになる区間**ができている。棚に無いものは出せないので、
これは物理的にありえない。

集計は途中経過を潰してしまうので、**`GROUP BY` では絶対に見つからない**。
実際に確かめた例（残3個のところへ7個の廃棄を遡って挿入した場合）:

| | 結果 |
|---|---|
| `SUM(...)` で期間合計 | `36` — 何の異常も見えない |
| `SUM(...) OVER (ORDER BY occurred_at)` | 途中で **`-4`** になる時点が見つかる |

「使えば楽になる近道」ではなく「**それでしか見えないもの**」を置くことで、
Window Function を学ぶ必然性が生まれる。

**obj-04 が二段構えの入口。** ここで「過去3回合っていたのは、正常だったからではない」
と疑い始める。廃棄が突出していなければ、obj-03 の「ズレは直近だけ」で
話が終わってしまう。

**obj-05 が決定打の半分。** `LEFT JOIN ... WHERE 承認.id IS NULL`（または `NOT EXISTS`）。
ここで**過去の期間にも無承認廃棄が見つかる**のが、このCASEで一番効く瞬間。

**obj-06 が決定打のもう半分。** 無承認廃棄というだけなら手続きミスかもしれない
（実際、おとりとして1件仕込む）。**起きた日より後に登録されている**ことが、故意の証明になる。

新概念は **列を定数ではなく別の列と比べる**こと。地味だが、最初はなかなか出てこない発想で、
「2つの時刻を持つテーブル」を読むときの基本動作になる。

```sql
WHERE m.created_at > m.occurred_at
```

ISO 形式の TEXT なので、これだけで成立する。日付関数は要らない。

## 5. 判定設計

### 計算結果そのものを判定に使わない

判定エンジンの列照合は**列名（大小文字は無視）**で行う
（`checks.ts` の `resolveColumns`）。つまり

```sql
SELECT ..., SUM(...) OVER (...) AS book_quantity FROM ...
```

の集計値を判定条件にすると、**プレイヤーが付けた別名と一致しないと落ちる**。
`book_qty` でも `帳簿在庫` でも `stock` でも正解であるべきなのに、判定が通らない。
これは「同じ結果に辿り着けば書き方は自由」（[ADR-0004](../adr/0004-answer-checking.md)）に真っ向から反する。

**したがって、判定は常に「その計算をした結果として浮かび上がる行の識別子」に置く。**
計算しないと到達できないが、判定が見るのは元テーブルにある列（`code` / `counted_at` /
`movements.id` など）だけ、という形にする。

CASE 001 は全Objectiveが生データの行を判定していたので、この問題が表面化しなかった。
CASE 002 で初めて必要になる設計上の制約なので、明示しておく。

### Objectiveごとの判定方針

| # | 判定 | 計算しないと到達できない理由 |
|---|---|---|
| obj-01 | `containsRows` on `stocktakes`（`counted_at='2026-06-16'` の行）+ `maxRows` | — |
| obj-02 | `columnValues` on `kind` = `['in','out','disposal']` exact + `maxRows` | SX-400 に絞る必要がある |
| obj-03 | `columnValues` on `occurred_at` = 在庫がマイナスになる時点 **exact: true** | 累積和を出さないと、途中でマイナスになった時点は見えない |
| obj-04 | `columnValues` on `code` = `['SX-400']` exact | 商品ごとの廃棄比率を出さないと1件に絞れない |
| obj-05 | `containsRows` on 無承認廃棄の `movements.id` 群 + `maxRows` | 承認テーブルとの突き合わせが必須 |
| obj-06 | `containsRows` on 遡及登録された `movements.id` 群 + `maxRows` | `created_at` と `occurred_at` を比べないと、おとりの1件を外せない |
| obj-07 | `columnValues` on `name` = `['相沢 亮']` **exact: true** | 無承認廃棄の記録者を集計する必要がある |

**`maxRows` は全Objectiveに付ける**（[case-format.md §8](../case-format.md)）。
`SELECT * FROM movements` のような全件ダンプで通らないようにするため。

### seed.sql が満たすべき条件

判定を `exact: true` で置く箇所があるので、データ側に厳密な要求が生まれる。
1行ずれるだけで、正解SQLを書いたプレイヤーが落ちる。
**seed.sql を書いたら、以下を機械的に検算すること**（`case-002.test.ts` に入れる）。

**在庫の整合性**

1. 各棚卸し日時点の `movements` 累積が、その日の `counted_quantity` と一致する（直近を除く）
2. 2026-06-16 時点だけ、累積 − 実地 = 12
3. 他商品でも 1 の検算が通る（差異を仕込んだ商品を除く）
4. `occurred_at` が棚卸し日と**同日**の movement を置かない
   （「棚卸しの前か後か」で解釈が割れ、正解が2通りになる）

**マイナス在庫（obj-03 の judgement）**

5. 累積在庫がマイナスになる時点が**ちょうど狙った数だけ**存在する。
   偶然マイナスになる区間を作ってしまうと、`exact` の判定が割れる
6. マイナスになるのは SX-400 だけ。他商品では起きない

**遡及記録（obj-06 の judgement）**

7. **正規の記録はすべて `created_at` = `occurred_at`**（完全一致）。
   1秒でもずらすと、`created_at > occurred_at` で正規の記録まで拾ってしまう
8. 遡及記録は `created_at > occurred_at`。かつ「棚卸しの直前に登録されている」ことが
   結果を目で見て分かる日付にする（判定条件にはしないが、ストーリー断片で触れる）

**4番と7番が特に見落としやすい。** どちらも境界の1行が正解を割る。

## 6. 難易度上のノイズ（意図的に混ぜるもの）

- **他商品の正常な廃棄**: 各商品に数件ずつ。承認レコードもある。
  「廃棄＝怪しい」ではないことを示す
- **別スタッフの無承認廃棄を1件**: 数量1。**その場で登録している**（`created_at` = `occurred_at`）
  ので、承認を取り忘れただけの純粋な手続きミス。
  → **「無承認廃棄＝犯人」の短絡を1度外す。** obj-06 が要る理由がこれ。
  obj-05 では拾われ、obj-06 で落ちる——この差が「うっかり」と「故意」の境目になる
- **差異が出ている別商品を1つ**: ただし正規の返品記録で説明がつく。
  → 「差異＝不正」の短絡を外す
- **退職済みスタッフ1名**: `status='retired'`。CASE 001 の学習が効くが、今回は無関係
- **夜勤帯の記録は複数スタッフが持つ**: 「夜勤＝犯人」にならないようにする

**入れないもの**: 6つ目のテーブル。[§3](#テーブル数を5にする判断)の通り5を上限とする。

### 誤答の選択肢（と、それを置く理由）

**犯人の候補**

- 検品担当（承認者）— 承認する側が怪しいという筋。無承認廃棄の意味を取り違えていると選ぶ
- 別の倉庫係 — 手続きミスで無承認廃棄が1件ある人物。obj-06 を飛ばすとここに着地する
