## 1. あらすじ

精密機器メーカーの研究棟から、試作機 **TX-7** が消えた。

持ち出し台帳には記録が残っている——6月12日に研究第2部の**森本 涼**が持ち出し、
翌13日の**午前3時12分に返却**。台帳の上では、TX-7 は棚に戻っている。
だが棚には無い。

入退館記録を当たると、その夜に第3研究室の扉を通ったのは
**森本のカードだけ**だった。話はそこで終わりそうに見える。

終わらない理由は、扉の仕様にある。

> 研究棟の扉は自動扉で、**前の人が開けた扉に続いて通ると記録が残らない。**
> だから正しい記録は必ず「入 → 出 → 入 → 出」と交互に並ぶ。
> **同じ向きが2回続いていたら、その間に記録の無い通行がある。**
>
> 一方、本館の正面玄関は回転扉で、1人ずつしか通れない。
> **こちらの記録には漏れが無い。**

森本のカードの記録は、交互になっていない。

## 2. 前作からの差分

| | CASE 001 | CASE 002 | **CASE 003** |
|---|---|---|---|
| 難易度 | 1 | 2 | **3** |
| テーブル | 4 | 5 | **6** |
| 主役の構文 | `JOIN` / サブクエリ | `SUM() OVER`（累積和） | **`LAG` / `LEAD`（隣接行・区間）** |
| 嘘の形 | 記録の中身が異常 | 記録が**後から足された** | **記録が「無い」ことが異常** |

CASE 002 は「並びの**累積**を見ると矛盾が出る」だった。
CASE 003 は「並びの**隣どうし**を見ると矛盾が出る」。
どちらも `GROUP BY` では潰れてしまう情報で、狙う筋肉が違う。

そして今回の嘘は**書き足し**ではなく**欠落**である。
「無い記録」は `WHERE` では探せない。そこが今回の一番の壁になる。

## 3. テーブル設計

### 判定に使う列名を、他テーブルと衝突させない

判定エンジンの列照合は**列名（大小文字は無視）**で行う
（`checks.ts` の `resolveColumns`）。`staff.name` と `doors.name` が両方あると、
`SELECT s.name, d.door_name` のつもりで `SELECT s.name, d.name` と書いたときに
**どちらが判定されるか決まらない**。

`id` や `occurred_at` が複数テーブルにあるのは普通のDB設計で、避けようがない。
避けるべきは、**判定に使う「意味のある列」**の衝突。

CASE 003 は `staff.name` を判定に使うので、
`doors.door_name` / `equipment.model_name` という別の列名にして衝突を避ける。

> **既存CASEの状況（実測）**
>
> | CASE | 判定に使う列の衝突 |
> |---|---|
> | case-001 | 無し（`name` は `employees` だけ。`occurred_at` は3テーブルにあるが、判定と同時に並べる場面が無い） |
> | case-002 | **`name` が `products` と `staff` の両方にある。** obj-07 は `name` で判定している |
>
> case-002 のこれは**誤って合格することはない**（別の列を見て落ちるだけ）が、
> 「`SELECT p.name, s.name` と書いた惜しい解が落ちる」余地は残っている。
> 実害が出ていないので今回は触らないが、
> [case-format.md](../case-format.md) のチェックリストに

### 各Objectiveの狙い

#### obj-01 / obj-02 は助走

6テーブルの構造と、データの語彙（`direction` の2値、`gate_type` の2値、
`revoked_on` の NULL）を、難しい操作抜きで掴ませる。
ここで「深夜に通ったのは森本のカードだけ」という**偽の結論**を一度掴ませるのが大事で、
obj-03 以降はそれを崩していく道のりになる。

#### obj-03 が主役の前半 — `LAG`

```sql
SELECT card_id, door_id, occurred_at, direction
FROM (
  SELECT card_id, door_id, occurred_at, direction,
         LAG(direction) OVER (PARTITION BY card_id, door_id ORDER BY occurred_at) AS prev
  FROM access_logs
)
WHERE prev = direction
```

**`GROUP BY` では絶対に見つからない**ことを、データで保証してある。

| 数え方 | C-1042 の結果 |
|---|---|
| カードごとの `in` / `out` の数 | **3 / 3** — 釣り合っている |
| カード×扉ごとの数（第3研究室） | **2 / 2** — 釣り合っている |
| カード×扉ごとの数（連絡通路） | **1 / 1** — 釣り合っている |
| 並びを隣どうしで比べる | **02:47 と 03:16 で違反** |

数を数えるどの切り口でも異常が出ないように組んである。
**順序を潰さずに隣を見ることでしか見えない。**

##### `PARTITION BY` に扉を入れないと引っかかる

カードだけで区切ると、**無関係な4枚が違反として出る**（実測）。

```
早瀬: in(連絡通路) → in(第1研究室) → out(第1研究室) → in(資材倉庫) → ...
```

連絡通路を通ってから研究室に入るのは**正常**で、扉ごとに見れば交互になっている。
このかたちの人が館内に何人もいるので、扉を入れ忘れると結果が一気に濁る。

| `PARTITION BY` | 出るカード |
|---|---|
| `card_id, door_id` | **C-1042 だけ** |
| `card_id` のみ | C-1002（早瀬）/ C-1042 / C-1071（里見）/ **C-1187（森本の新カード）** |

とくに **C-1187 が混ざる**のが厄介で、
「森本の新カードも怪しい」という誤った筋に入りかねない。
意地悪ではなく、**「どの単位で並べるか」を考えさせるための道標**として置く。
ヒント2で明示する。

#### obj-04 / obj-05 は二段構えの土台

- **obj-04**: 「森本のカードが通った」は「森本が通った」ではない。
  紛失した旧カードが失効していない、という運用の穴を見つける
- **obj-05**: 森本は 21:48 に帰宅している。**03:12 の「返却」時に建物にいない**。
  台帳の返却記録が偽物だと分かる

この2つが揃って、はじめて「森本ではない誰か」が確定する。

#### obj-06 が主役の後半 — `LEAD`

02:47（記録の無い通行があった時刻）に、建物の中にいたのは誰か。

正面玄関は回転扉で記録に漏れが無いので、**入館と退館を対にすれば在館区間が作れる**。

```sql
WITH gate AS (
  SELECT c.holder_id, a.direction, a.occurred_at,
         LEAD(a.occurred_at) OVER (PARTITION BY a.card_id ORDER BY a.occurred_at) AS next_at
  FROM access_logs a
  JOIN doors d ON d.id = a.door_id
  JOIN cards c ON c.id = a.card_id
  WHERE d.door_name = '正面玄関'
)
SELECT s.name
FROM gate g JOIN staff s ON s.id = g.holder_id
WHERE g.direction = 'in'
  AND g.occurred_at <= '2026-06-13 02:47:00'
  AND (g.next_at IS NULL OR g.next_at > '2026-06-13 02:47:00')
```

**境界をノイズにしてある。**

| 人物 | 直前の動き | 02:47 に | 間違えやすい点 |
|---|---|---|---|
| 里見 | **01:55 退館** | 外 | 「その日に入館した人」で拾うと入ってしまう |
| 阿久津 | **03:30 入館** | 外 | 「その日に館内にいた人」で拾うと入ってしまう |
| 森本 | 21:48 退館 | 外 | 日付をまたぐので `date()` で切ると消える |
| 久我山 | 09:10 入館 → 04:05 退館 | **中** | 入館が前日 |
| 早瀬 | 20:00 入館 → 08:00 退館 | **中** | |

区間の端の扱いを雑にすると答えが変わる。**`LEAD` を学ぶ意味がここにある。**

#### obj-07 が決定打 — 「無い」ことを示す

久我山と早瀬のどちらか。決め手は**自分名義のカードで研究棟の扉を通った記録が無いこと**。

- 早瀬は巡回で連絡通路・第1研究室・資材倉庫に記録がある
- 久我山は研究棟の扉に**一度も**記録が無い。なのに 04:05 に退館している

つまり久我山は、自分のカードを使わずに研究棟を出入りした。
そして同じ時間帯に、森本の旧カードが研究棟を出入りしている。

```sql
SELECT s.name FROM staff s
WHERE s.id IN (2, 4)  -- obj-06 で絞った2名
  AND NOT EXISTS (
    SELECT 1 FROM access_logs a
    JOIN cards c ON c.id = a.card_id
    JOIN doors d ON d.id = a.door_id
    WHERE c.holder_id = s.id AND d.building = '研究棟'
      AND a.occurred_at >= '2026-06-13 00:00:00'
      AND a.occurred_at <  '2026-06-13 06:00:00'
  )
```

新概念は **`NOT EXISTS`（相関サブクエリの否定）**。
CASE 002 の `LEFT JOIN ... IS NULL` と同じ「無いことを探す」問題だが、
今回は**条件が複数テーブルにまたがる**ので `LEFT JOIN` では書きにくい。
そこが次の段階になる。

## 6. 判定設計

### 計算結果そのものを判定に使わない

CASE 002 と同じ原則。`LAG(...) AS prev` のような**プレイヤーが名付ける列**を
判定条件にしない。判定は必ず**元テーブルの列名と値**で行う。

### 各Objectiveの判定

| # | 判定 | 上限行数 | 意図 |
|---|---|---|---|
| obj-01 | `containsRows` `asset_tag='TX-7'`, `returned_at='2026-06-13 03:12:00'` | 6 | 台帳を引けたこと |
| obj-02 | `columnValues` `card_number` = `['C-1042']`（exact） | 6 | 深夜の第3研究室に絞れたこと |
| obj-03 | `columnValues` `card_number` = `['C-1042']`（exact） | 6 | **扉ごとに区切れたこと**（カードだけだと4枚出て落ちる） |
| obj-04 | `columnValues` `name` = `['森本 涼']`（exact） | 4 | 有効カードが複数ある人物 |
| obj-05 | `containsRows` `card_number='C-1187'`, `direction='out'`, `occurred_at='2026-06-12 21:48:00'` | 8 | 森本の帰宅時刻 |
| obj-06 | `columnValues` `name` = `['久我山 慧', '早瀬 拓']`（exact） | 2 | **区間の端を正しく扱えたこと** |
| obj-07 | `columnValues` `name` = `['久我山 慧']`（exact） | 1 | 特定 |

`exact: true` の `columnValues` は**集合一致**なので、
1人でも余計に混ざれば落ちる。境界ノイズがそのまま判定に効く。

**すべての `containsRows` に `maxRows` を付ける**（全件ダンプ対策）。

### obj-03 の判定を `card_number` にする理由

違反行そのもの（`occurred_at` の集合）で判定すると、
`PARTITION BY card_id` だけの惜しい解が落ちる——それは意図どおりだが、
「どの行を出すか」の書き方の自由度まで奪ってしまう
（違反行だけを出すか、前後2行を出すか、で結果が変わる）。

**`card_number` の集合**で判定すれば、
「扉ごとに区切れていれば C-1042 だけが出る / カードだけだと4枚出る」
という**判定したい一点**だけを見られる。

| 里見の旧カードは**正しく失効している** | 「再発行＝穴」ではないことを示す対比 |

| 森本の記録が前日 06-12 にまたがる | `date(occurred_at) = '2026-06-13'` で切ると消える |

3問。

2. **使われたカードの番号は** → C-1042
3. **発覚が遅れた理由は**（選択式）→ 台帳に偽の返却が登録されていたため

## 9. エピローグの要件

- **森本は無実**であることをはっきり書く。カードを紛失し、届も出していた
- 悪いのは**失効させなかった運用**であることに触れる。
  犯人が特別に賢かったわけではなく、穴が開いていた
- 「記録が無い」ことが証拠になった、という筋を残す。
  このCASEで学んだのは `LAG` / `LEAD` の構文ではなく、
  **並びの隙間を見るという発想**

---

## 10. 決まったこと / まだ開いていること

### 決まったこと

- 主役は `LAG` / `LEAD`。どちらも `GROUP BY` では届かない位置に置く
- 嘘の形は「欠落」。CASE 002 の「書き足し」と対にする
- 日付の**引き算をしない**。`julianday` などの方言関数を使わずに解けるようにする
  （CASE 002 でのフィードバックを引き継ぐ）。
  時刻は ISO 形式の TEXT なので、大小比較だけで足りる
- 列名は6テーブルを通して一意にする

### まだ開いていること

- **想定時間 40〜75分**は仮。CASE 002 が実測 30〜60分だったので、
  Objective 1本ぶんと概念1つぶんを足した見積もり。実プレイで直す
- **obj-07 を独立させるか、obj-06 に畳むか。**
  独立させると 7本になり CASE 002 と同じ長さになる。
  畳むと `LEAD` と `NOT EXISTS` を1本で問うことになり、重い。
  いまは独立させる案で書いている
- **ER図の配置**。6テーブル・5リレーションを 900×560 に収めつつ、
  線の交差・並走・箱の貫通を避ける（幾何テストが自動で見る）。
  実装時に総当たりで詰める
